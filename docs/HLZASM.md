# HLZASM / ZSPU language reference

This documents the actual language the scripts generated by this project (`CreateFileString` in
`src/utilityfunctions.ts`) are written in, and the runtime that executes them. It's sourced by
reading the Wiremod `wire` addon's source directly (Lua, GPL), not from any official spec — there
isn't one distributed separately from the source.

Kept here because it's directly relevant to what this project generates, but the language itself
is general-purpose across Wiremod's whole "PU" chip family (CPU/GPU/SPU all share it), not
specific to MIDI conversion — worth knowing if this ever gets used for something bigger than the
converter.

**Sources** (sparse-cloned locally at `E:\projects\wire`, not part of this repo):
- `lua/wire/cpulib.lua` — the shared virtual machine + the authoritative instruction table
  (`CPU()`/`GPU()`/`VEX()`/`SPU()` entries, ~line 1291 to EOF).
- `lua/wire/client/hlzasm/` — the HLZASM compiler: `hc_tokenizer.lua` (keywords/tokens),
  `hc_syntax.lua` (statement/block grammar), `hc_expression.lua` (expression parsing),
  `hc_compiler.lua` (driver), `hc_codetree.lua`/`hc_output.lua` (codegen), `hc_optimize.lua`.
  Not fully read line-by-line — see "Unverified" at the bottom before relying on anything not
  covered here (control-flow codegen details, macro/preprocessor semantics, struct layout rules).
- `lua/entities/gmod_wire_spu/{init,cl_init,cl_spuvm,shared}.lua` — the SPU entity: how it wires
  up the VM, the sound-channel model, and the SPU-specific opcode implementations.

## Two dialects, one compiler

The tokenizer (`hc_tokenizer.lua`) recognizes two language modes side by side: **ZASM** (raw
assembly — one instruction per line, no braces/control-flow sugar) and **HLZASM** ("High-Level
Z-ASM" — adds `{ }` blocks, `if`/`while`/`for`/`switch`, typed declarations, functions, operators).
Everything below is HLZASM, which is what this project's generated scripts use and what the Lua
entity's edit UI presents.

## VM / runtime model

Each chip (CPU, GPU, SPU) is an instance of the same generic virtual machine (`cpulib.lua`) with a
different `CPUTYPE` and a different opcode extension loaded on top:
- General-purpose registers `EAX EBX ECX EDX ESI EDI ESP EBP`, extended registers `R0`-`R31`,
  segment registers `CS SS DS ES GS FS KS LS`.
- Flat memory space, memory-mapped I/O via `PORT` operands (`IN`/`OUT`/`HALT`), plus a few
  special addresses used as hardware control registers (e.g. `65535` = clock enable, `65534` =
  reset, checked in `gmod_wire_spu/cl_spuvm.lua`'s overridden `WriteCell`).
- 32-bit-ish memory cells that hold either integers or floats depending on precision mode
  (`BPREC`/`IPREC` registers; default is 48-bit float mode) — see `VM:Reset()` in `cl_spuvm.lua`.
- No implicit entry point by name. Execution starts at address 0 and runs linearly through the
  compiled instruction stream like real assembly — a `void main() {}` function is not special to
  the compiler, it only "runs first" if nothing jumps around it and control simply falls into it
  after the preceding top-level statements (this is how this project's generated scripts work: a
  setup preamble runs, falls through into `main()`, which self-loops forever via `jmp main;`).
  **This specific point is inferred from the shape of the generated script, not independently
  confirmed by reading the linker/codegen stage** — verify against `hc_output.lua` before relying
  on it for anything more elaborate (e.g. multiple top-level functions, expecting a specific one
  to run first by name).
- The SPU variant (`ChipType`/`CPUTYPE = 2`) removes a chunk of the base instruction set that
  doesn't make sense for it (paging, protected mode, interrupts-related opcodes, memory
  mapping — see the `self.VM.OperandCount[n] = nil` block in `OverrideVM()` in `cl_spuvm.lua`) and
  adds its own sound opcodes (below).

## HLZASM syntax

- **Comments**: `//` line comments, `/* */` block comments.
- **Types**: `void`, `float`, `char`, `int48`, `vector` (`VECTOR1F`/`VECTOR2F`/`VECTOR3F`/`UV`/...
  subvariants). There's no separate `int`/`short`/`double` — `int48` and `float` are it. `string`
  is a distinct declaration form (`STRALLOC` token) for string literals/buffers, not a `TYPE`.
  Pointers use a `*` suffix on the type (`char* str`), arrays use a `[size]` suffix on the name.
- **Declarations**: `type name;`, `type name, name2;`, `type name = value;`, top-level globals and
  local-in-function declarations both use this form. `string name,"literal";` declares a named
  string constant (used for the waveform filename in this project's generated scripts).
- **Functions**: `returnType name(paramType paramName, ...) { ... }`. Modifiers: `export`,
  `inline`, `forward` (forward-declare before definition). `return expr;` inside a non-`void`
  function.
- **Control flow**: `if`/`else`, `while`, `do`/`while`, `for`, `switch`/`case`, `goto` + labels
  (`label:`), `break`, `continue`.
- **Operators**: arithmetic `+ - * / %`, bitwise `& | ^` and shifts `<< >>`, a power operator
  `^^`, increment/decrement `++ --`, comparisons `== != <= < >= >`, logical `! && ||`, assignment
  `=` and compound `+= -= *= /=`.
- **`struct`**: user-defined structure types (`struct Name { ... }`), fields accessed with `.`.
  Not used by this project's generator — semantics not verified beyond the tokenizer recognizing
  the keyword and `hc_syntax.lua` having a struct-parsing branch (~line 910).
- **Data statements**: `db value, value, ...;` emits raw data cells inline (this project's
  generator uses this for the note-number arrays, 32 values per `db` line, terminated by
  `db 0; // End string` — see `createDbLines` in `src/utilityfunctions.ts`). `alloc`, `#define`,
  `code`/`data`/`org`/`offset` also exist as lower-level placement/preprocessor directives — not
  used by this project and not further verified here.

### Instructions are callable as statements

Any opcode from the instruction table below can be written directly as a statement, function-call
style: `MNEMONIC operand1, operand2;` (case-insensitive; this project's generator emits lowercase,
e.g. `wset 0,trackwave;`, `chpitch 0,note;`, `mod i,tracklen;`, `jmp main;`). This is the main way
HLZASM differs from an ordinary C-like language — raw processor instructions and high-level
control-flow/expressions are freely mixed in the same source file. `fpwr note,(track0[i]/12);` in
this project's generated `main()` loop, for example, is a direct call to the `FPWR` opcode (raise
X to power Y), not a library function.

`cl_spuvm.lua` (opcodes 335-337) are empty function bodies — they're accepted but do nothing.

## SPU audio model (why the generated scripts sound like they do)

- Up to 32 sound channels (`WireSPU_MaxChannels`). Each channel plays one waveform, independently
  pitched/volumed/enveloped.
- 4 waveform slots are pre-loaded on reset: slot 0 = `synth/square.wav`, 1 = `synth/saw.wav`,
  2 = `synth/tri.wav`, 3 = `synth/sine.wav`. `WSET` can rebind *any* slot number 0-8191 to an
  arbitrary Source-engine sound resource path — this project's generator does exactly that,
  binding one slot per channel (`wset i,trackwave;`) to the same `"synth/sine_880.wav"` for every
  channel (a variable named `trackwave`, not one of the 4 default slots). **Every channel this
  project generates uses an identical plain sine voice** — there's no per-instrument timbre
  variation; General MIDI program/instrument numbers are not read or used anywhere in this
  project's pipeline.
- Pitch: `CHPITCH`'s implementation does `Sound:ChangePitch(clamp(X*100, 0, 255), 0)` — X is a
  *ratio* (1.0 = unchanged playback rate), converted to a percentage internally. This project's
  generator computes that ratio per note as `2 ^ (midiNoteNumber / 12)` (via `FPWR`, then divides
  by 100 before the call, since `CHPITCH` re-multiplies by 100 internally) — i.e. playback speed
  doubles every 12 semitones, which is musically correct *shape* but has no reference-pitch
  offset: raw MIDI note 0 maps to 100% (unchanged) speed of the base sine sample, not to any
  particular absolute frequency. This is an existing quirk of the generator, not something fixed
  in this session — worth knowing if pitch mapping is ever revisited.
- ADSR envelope (`CHADSR`'s 4-float vector = attack ms, decay ms, sustain level 0-1, release ms)
  is implemented client-side in `VM:CalculateADSR` (`cl_spuvm.lua`). This project's generator
  never calls `CHADSR`, so every channel keeps the VM's default envelope
  (`{x=0, y=0, z=1, w=0}` — instant attack, no decay, full sustain, instant release).
